# رُمّان · RUMMAN

**منصّة سوبر ماركت متعدّدة الفروع — جاهزة للتشغيل الفعلي.**

`React 18` · `Vite` · `Node.js` · `Express` · `MySQL 8` · `JWT`

</div>

---

## ما هذا؟

متجر إلكتروني كامل لسلسلة سوبر ماركت في مصر، بواجهة عربية RTL،
وهوية بصرية مبنيّة على فكرة **الرمّانة**: قشرةٌ داكنة واحدة تضمّ حبّاتٍ
ياقوتية كثيرة — تمامًا كأقسام المتجر تحت سقف واحد.

**المشروع يبدأ فارغًا.** لا فروع وهمية ولا منتجات عيّنة ولا طلبات
مخترعة ولا حسابات تجربة. أوّل تشغيل يعطيك حساب مدير واحدًا وقائمة
تحقّق، وتبني متجرك الحقيقي من لوحة الإدارة.

## التشغيل

### ١) المتطلّبات
- Node.js **18.18+**
- MySQL **8.0+** (أو `docker compose up -d` لتشغيلها جاهزة)

### ٢) التثبيت
```bash
npm run install:all
```

### ٣) الإعدادات
```bash
cp server/.env.example server/.env
```

ثم املأ الحدّ الأدنى في `server/.env`:

```bash
# ولّد كل سرّ بأمر مستقلّ
openssl rand -base64 48   # ← JWT_ACCESS_SECRET
openssl rand -base64 48   # ← JWT_REFRESH_SECRET
```

وبيانات قاعدة البيانات، وبيانات حسابك كمدير (`ADMIN_*`).

### ٤) إنشاء القاعدة والحساب الأول
```bash
npm run db:setup
```

يُنشئ الجداول، ثم حساب المدير من متغيّرات `ADMIN_*`.
أو مرّرها مباشرة:

```bash
npm run db:bootstrap -- --name="اسمك" --email="you@domain.com" --phone="01xxxxxxxxx" --password='كلمة-مرور-قوية'
```

> بعد نجاح الإنشاء **احذف `ADMIN_PASSWORD` من `.env`**.

### ٥) التشغيل
```bash
npm run dev
```

| الخدمة | العنوان |
|---|---|
| الواجهة | http://localhost:5173 |
| الـ API | http://localhost:4000/api/v1 |
| فحص الصحّة | http://localhost:4000/health |

## بناء متجرك (أول ٢٠ دقيقة)

ادخل بحساب المدير ثم افتح `/admin`. الشاشة الأولى تعرض قائمة تحقّق
حيّة تقول لك ما ينقص. الترتيب مهمّ:

| # | الخطوة | لماذا هذا الترتيب |
|---|---|---|
| ١ | **الفروع** | الفرع يحمل السعر والمخزون ورسوم التوصيل ونطاق التغطية. لا شيء يعمل قبله. الإحداثيات من خرائط جوجل (زرّ أيمن ← نسخ الرقمين) لأن «أقرب فرع» يُحسب بالمسافة الفعلية. |
| ٢ | **الأقسام** | لكل قسم لون وزخرفة — منهما تُبنى الصفحة الرئيسية وبطاقات المنتجات وأشرطة التقارير. |
| ٣ | **العلامات** *(اختياري)* | المزارع والموردون — اسم المُنتِج الذي يظهر على البطاقة. |
| ٤ | **المنتجات** | واحدًا واحدًا، أو **استيراد ملف** لكتالوج كامل. |
| ٥ | **المخزون** | المنتج لا يُباع في فرع إلّا إن كان مُدرجًا في مخزونه. من شاشة المنتجات ← أيقونة المخزون تنشره على كل الفروع دفعةً واحدة. |

### استيراد الكتالوج من Excel

`/admin/import` — ثلاث خطوات لا تُختصَر:

1. **نزّل القالب** — ملف CSV بترميز عربي صحيح وأسماء أعمدة مضبوطة.
2. **ارفع واقرأ التقرير** — الأخطاء مرقّمة بالسطر كما تراه في Excel.
3. **طبّق** — لا يُفتح الزرّ إلّا بعد فحصٍ نظيف، والتطبيق في معاملة
   واحدة (إمّا الكل أو لا شيء).

الأقسام والعلامات تُنشأ تلقائيًا بأسمائها. الكود (SKU) هو المفتاح،
فإعادة رفع نفس الملف بعد تعديل الأسعار **تُحدِّث ولا تُكرِّر**.

## وسائل الدفع

ثلاث وسائل، لكلٍّ تدفّق مختلف جوهريًا. وما لا تُفعِّله **لا يظهر
للعميل أصلًا** — فلا يختار وسيلةً غير جاهزة ثم يفشل طلبه.

### الدفع عند الاستلام
```bash
PAY_COD_ENABLED=true
```
يُحصَّل لحظة التسليم. يسجّله الفرع من اللوحة أو يُحتسب تلقائيًا عند
تحويل الطلب إلى «تم التسليم».

### إنستاباي
```bash
PAY_INSTAPAY_ENABLED=true
INSTAPAY_ADDRESS=your-address@instapay
INSTAPAY_ACCOUNT_NAME=اسم الحساب
```

لا توجد واجهة برمجية للتجّار في الشبكة المصرية، فالتدفّق الحقيقي:

```
العميل يحوّل ← يرفع صورة الإيصال ورقم العملية
  ← الطلب تحت المراجعة ← الفريق يعتمد أو يرفض من /admin/payments
  ← يبدأ التجهيز
```

لا شيء يُعتبر مدفوعًا إلّا باعتماد بشري مسجَّل باسم من اعتمده ووقته
في سجلّ التدقيق. الإيصالات تُفحَص بمحتواها الفعلي (magic bytes) لا
بامتدادها.

### فوري
```bash
PAY_FAWRY_ENABLED=true
FAWRY_MERCHANT_CODE=...
FAWRY_SECURITY_KEY=...
FAWRY_BASE_URL=https://www.atfawry.com     # الاختبار: https://atfawry.fawrystaging.com
```

تكامل فعلي بنموذج `PAYATFAWRY`: نطلب كود دفع، ويسدّده العميل من أي
منفذ فوري أو تطبيق myFawry، وتستدعي فوري نقطة الإشعار عندنا.

**مهمّ:** اضبط `API_PUBLIC_URL` على العنوان العام للـ API، وسجّل في
لوحة تاجر فوري:

```
<API_PUBLIC_URL>/api/v1/payments/fawry/notify
```

كل إشعار وارد يُؤرشَف قبل معالجته، ويُتحقَّق من توقيعه، ولا يُعتمد
دفعٌ بمبلغ أقلّ من إجمالي الطلب.

## البريد الإلكتروني

```bash
RESEND_API_KEY=re_...
MAIL_FROM=رُمّان <orders@your-domain.com>
```

1. أنشئ حسابًا على [resend.com](https://resend.com)
2. أضف نطاقك وفعّل سجلّات DNS
3. أنشئ مفتاح API

الرسائل المرسَلة: تفعيل البريد · استعادة كلمة المرور · تأكيد الطلب ·
تحديث الحالة · تأكيد الدفع · كود فوري. كلّها قوالب عربية RTL.

**بدون مفتاح** يعمل النظام في «وضع السجلّ»: تُكتب الرسائل في سجلّ
الخادم بدل إرسالها، مع تنبيه في كل مرّة. البريد لا يُسقِط طلبًا أبدًا.

## المميّزات

### التسوّق
- **تعدّد فروع حقيقي** — سعر ومخزون وممرّ ورسوم توصيل مستقلّة لكل فرع،
  مع اختيار أقرب فرع بالإحداثيات (هافرساين).
- بحث فوري باقتراحات، و«الأكثر بحثًا»، وسجلّ بحث محلّي.
- فلاتر مركّبة (قسم، سعر، تقييم، عضوي، حصري، مخفّض، متوفّر) — كلها في
  الرابط فيمكن مشاركتها.
- توفّر المنتج **في كل الفروع** معروض داخل صفحته.
- «يُشترى معه عادةً» محسوبة من طلبات حقيقية، و«شاهدت مؤخرًا».
- تقييمات **بشراء موثّق فقط**، مع توزيع النجوم وتصويت «مفيد».
- مفضّلة تعمل للزائر والمسجّل.

### السلة والطلب
- سلة محفوظة في الخادم لكل (عميل × فرع)، وسلة محلّية للزائر تُدمج
  تلقائيًا عند تسجيل الدخول.
- كوبونات بأربعة أنواع بسقوف وحدود استخدام لكل عميل.
- مواعيد توصيل بشرائح وسعة يومية، أو استلام من الفرع.
- استبدال نقاط الولاء حتى نصف قيمة السلة.
- إنشاء الطلب داخل **معاملة ذرّية** مع قفل صفوف المخزون (`FOR UPDATE`)
  — لا بيع زائد.
- تتبّع بخط زمني، إلغاء، إعادة طلب، وتقييم تجربة التوصيل.

### الحساب والولاء
- JWT مع **دوران توكنات التجديد** وعرض الأجهزة النشطة.
- ثلاث فئات ولاء بترقية تلقائية ومضاعِف نقاط لكل فئة.
- محفظة برصيد وكشف حركة، واسترداد تلقائي عند الإلغاء.
- دفتر عناوين، إشعارات داخل التطبيق، كشف نقاط.

### الإدارة
- **قائمة تحقّق جاهزية** تقول ما ينقص المتجر ليبيع.
- CRUD كامل: فروع (+ مواعيد + مناطق توصيل)، أقسام، علامات، منتجات
  (+ صور + مخزون)، كوبونات، عروض، مستخدمون، إعدادات.
- استيراد CSV بمعاينة إلزامية.
- مؤشّرات أداء مع مقارنة بالفترة السابقة، ومنحنى إيراد يومي.
- طابور التجهيز ضمن آلة حالة صارمة، وطابور مراجعة التحويلات.
- سجلّ تدقيق لكل عملية كتابة: من فعل، وماذا، ومتى، ومن أي عنوان.
- **صلاحيات مفروضة في الخادم**: مدير الفرع يرى فرعه فقط.

### تقني
- تحقّق مدخلات بـ Zod على كل مسار، برسائل عربية على مستوى الحقل.
- حدود معدّل متدرّجة، Helmet، CORS بقائمة بيضاء، ضغط، معرّف طلب.
- رفع ملفات بأربع طبقات حماية (اسم مولَّد، فحص المحتوى، حدّ حجم،
  ترويسات تمنع التنفيذ).
- حذف منطقي، حركات مخزون، فهارس على كل استعلام متكرّر.
- وضع ليلي كامل، ووصولية حقيقية: تركيز واضح، ARIA، حبس تركيز في
  النوافذ، احترام `prefers-reduced-motion`، و**حساب تباين النصّ على
  ألوان الأقسام رياضيًا** (WCAG) بدل افتراضه.
- تقسيم حزم: كل صفحة في قطعة مستقلّة.

## الهيكل

```
rumman/
├── database/schema.sql          ← 36 جدولًا + عرضان + محفّزات
│
├── server/src/
│   ├── config/                  ← البيئة، الاتصال، ثوابت العمل
│   ├── middleware/              ← مصادقة، صلاحيات، تحقّق، رفع، حدود
│   ├── utils/                   ← أخطاء، استجابات، أمان، نقود، جغرافيا
│   ├── services/mailer/         ← Resend + قوالب عربية
│   ├── modules/                 ← 17 موديولًا (routes + service)
│   │   ├── admin/               ← CRUD + استيراد + سجلّ تدقيق
│   │   └── payments/            ← فوري + إنستاباي + كاش
│   ├── database/                ← migrate.js · bootstrap.js
│   └── routes/index.js          ← خريطة الـ API كاملة
│
└── client/src/
    ├── styles/                  ← توكنات + أساس + مكوّنات + تخطيط + منتج + صفحات + إدارة
    ├── lib/                     ← عميل API، أيقونات، زخارف، ألوان، تنسيق
    ├── data/content.js          ← النصوص الثابتة (بلا أي رقم أو اسم فرع)
    ├── context/                 ← Theme · Site · Toast · Branch · Auth · Wishlist · Cart
    ├── components/              ← brand · ui · layout · product · cart · home · checkout · account · admin
    └── pages/                   ← المتجر + الحساب + 13 شاشة إدارة
```

**ثلاث قواعد معمارية:**

1. **في الخادم:** المسار يستقبل ويتحقّق، والخدمة تحمل المنطق و SQL.
   لا SQL في المسارات ولا منطق في الواجهة.
2. **في الواجهة:** الصفحة تُركّب مكوّنات ولا ترسم تفاصيل. كل قسم بصري
   في ملفه، وكل نصّ ثابت في `data/content.js`.
3. **لا رقم مخترع في أي نصّ.** عدد الفروع والأقسام والمنتجات وبيانات
   التواصل تأتي كلّها من `/content/site` — فما يُعرض هو ما في القاعدة.

## أوامر

| الأمر | ماذا يفعل |
|---|---|
| `npm run dev` | الخادم والواجهة معًا |
| `npm run dev:server` / `dev:client` | أحدهما فقط |
| `npm run db:migrate` | إنشاء/إعادة إنشاء الجداول (**يمسح البيانات**) |
| `npm run db:bootstrap` | الإعدادات + حساب المدير الأول (آمن للتكرار) |
| `npm run db:setup` | الاثنان معًا |
| `npm run build` | بناء الواجهة للإنتاج |
| `npm start` | تشغيل الخادم في الإنتاج |

## النشر

راجع [docs/DEPLOY.md](docs/DEPLOY.md) للخطوات الكاملة.

قائمة ما قبل النشر — الخادم يرفض الإقلاع إن نقص أيٌّ من الأول:

- [ ] `NODE_ENV=production`
- [ ] `JWT_ACCESS_SECRET` و`JWT_REFRESH_SECRET` عشوائيان و32 حرفًا فأكثر
- [ ] `CLIENT_ORIGIN` نطاقك فقط — بلا `localhost` وبلا `*`
- [ ] `API_PUBLIC_URL` العنوان العام للـ API
- [ ] `SUPPORT_EMAIL` و`SUPPORT_PHONE`
- [ ] `RESEND_API_KEY` ونطاق البريد موثّق
- [ ] `FAWRY_BASE_URL` على الإنتاج لا الاختبار (إن فعّلت فوري)
- [ ] وسيلة دفع واحدة مفعّلة على الأقل
- [ ] HTTPS، وحذف `ADMIN_PASSWORD` من `.env`
- [ ] نسخ احتياطي دوري لقاعدة البيانات ومجلّد `server/uploads`

شاشة `/admin/settings` تعرض حالة هذه الإعدادات كلّها للتحقّق البصري
قبل النشر.
