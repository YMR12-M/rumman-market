## الخادم

### طبقات الموديول
كل موديول في `server/src/modules/<name>/` يتكوّن من:

| الملف | المسؤولية | ما لا يفعله |
|---|---|---|
| `*.routes.js` | تعريف المسارات وربط الـ middleware والتحقّق | لا يكتب SQL ولا منطق عمل |
| `*.validation.js` | مخططات Zod للمدخلات | لا يلمس قاعدة البيانات |
| `*.controller.js` | قراءة الطلب ← نداء الخدمة ← تشكيل الاستجابة | لا يحتوي قاعدة عمل واحدة |
| `*.service.js` | منطق العمل و SQL والمعاملات | لا يعرف شيئًا عن `req`/`res` |

الموديولات الصغيرة (المفضّلة، الإشعارات، الولاء) تدمج الطبقات في ملف
مسارات واحد عمدًا — إضافة أربعة ملفات لثلاث دوال تعقيد بلا فائدة.

### ترتيب الـ middleware (مقصود)
```
helmet → cors → json → compression → requestContext → morgan
  → /health
  → rateLimit → routes
  → notFound → errorHandler
```
`/health` قبل حدّ المعدّل ليعمل مع أدوات المراقبة بلا حجب.

### معالجة الأخطاء
- `ApiError` يحمل كود HTTP + رسالة عربية + كود داخلي + أخطاء حقول.
- `asyncHandler` يلتقط أي رفض ويمرّره لمعالج الأخطاء المركزي.
- أخطاء MySQL الشائعة (تكرار، مفتاح أجنبي، انقطاع) تُترجَم إلى رسائل مفهومة.
- في الإنتاج: أي خطأ غير متوقّع يُسجَّل كاملًا ويُعرض للعميل كرسالة عامة.

### المصادقة
```
دخول ──▶ access_token (30 دقيقة، JWT)
     └─▶ refresh_token (30 يومًا، عشوائي)
                │
                └─ يُخزَّن في القاعدة كـ SHA-256 فقط
                   كل استخدام يُبطله ويُصدر بديلًا (دوران التوكنات)
```
تسرّب قاعدة البيانات لا يمنح المهاجم جلسات، وتسرّب توكن واحد ينتهي أثره
عند أول تجديد شرعي.

### سلامة المخزون
إنشاء الطلب معاملة واحدة:
1. `SELECT … FOR UPDATE` على صفوف مخزون كل صنف (قفل).
2. التحقّق من `quantity - reserved` ثم زيادة `reserved`.
3. تسجيل حركة مخزون لكل صنف (سجلّ تدقيق).
4. إنشاء الطلب وأصنافه بلقطة أسعار ثابتة.
5. الكوبون والنقاط والمحفظة.
6. تفريغ السلة وإشعار العميل.

أي فشل ⇒ `ROLLBACK` كامل. عند **التسليم** يتحوّل الحجز إلى خصم فعلي،
وعند **الإلغاء** يُفكّ الحجز وتُعاد النقاط والرصيد.

### آلة حالة الطلب
```
pending → confirmed → preparing → ready → out_for_delivery → delivered → refunded
   │          │           │          │            │
   └──────────┴───────────┴──────────┴────────────┴──▶ cancelled
```
الانتقالات معرّفة في `config/constants.js` ويُرفض أي انتقال خارجها —
فلا يمكن قفز طلب من `pending` إلى `delivered`.

## الواجهة

### شجرة المزوّدات
```
ThemeProvider             ← الوضع الفاتح/الليلي
 └ ToastProvider          ← التنبيهات (يحتاجه الجميع)
    └ SiteProvider        ← بيانات المتجر الحقيقية من /content/site
       └ BranchProvider   ← الفرع المختار + الأقسام
          └ AuthProvider  ← المستخدم والتوكنات
             └ WishlistProvider
                └ CartProvider   ← يعتمد على الفرع والمستخدم معًا
```
الترتيب ليس عشوائيًا: كل مزوّد يستهلك ما فوقه.

`SiteProvider` هو ما يمنع الواجهة من كتابة أرقام مخترعة. عدد الفروع
والأقسام والمنتجات وبيانات التواصل وحدّ التوصيل المجاني تأتي كلّها
منه — فما يقرأه الزائر هو ما في القاعدة، ولا يصير نصٌّ كاذبًا يوم
يُغلق فرع.

### طبقة الخدمات
- `lib/api.js` — عميل HTTP: إرفاق التوكن، تجديده مرّة واحدة عند انتهائه
  (بطابور يمنع التجديدات المتوازية)، وتحويل الأخطاء إلى شكل موحّد.
- `services/catalog.service.js` — قراءة الكتالوج من الخادم مباشرة.
  **لا نسخة محلّية ولا وضع عرض:** كتالوجٌ مخزَّن في الواجهة يعرض أسعارًا
  ومخزونًا قد تغيّرا، وهذا أسوأ من رسالة خطأ صريحة.
- `services/admin.service.js` — مرآة مسارات `/admin` و`/payments`.
- كل الخدمات تتطلّب خادمًا فعليًا.

### السلة في وضعين
| | زائر | مسجّل |
|---|---|---|
| التخزين | `localStorage` بلقطة منتج | جدول `carts` في القاعدة |
| الإجماليات | تُحسب محليًا بنفس قواعد الخادم | تأتي من الخادم |
| الكوبونات | غير متاحة | متاحة |
| عند الدخول | **تُدمج تلقائيًا** ثم تُمسح | — |

### نظام التصميم
- كل لون ومقاس وخط في `styles/tokens.css`. لا قيمة صريحة في أي ملف آخر.
- الهوية «ياقوت ليلي + ذهب شمبانيا»: الأسود الخمري والذهب يحملان الفخامة،
  والياقوت للفعل وحده، وطيف الأقسام يحمل الزهو. راجع `docs/BRAND.md`.
- الوضع الليلي ليس قلبًا للأدوار بل **غرفة أخرى**: خمريّ عميق وذهبٌ على
  الحواف وياقوتٌ أكثر سطوعًا. يُستعاد قبل أول رسم بسكربت في `index.html`
  فلا تومض خلفية فاتحة.
- ألوان الأقسام تأتي من قاعدة البيانات، ولون النصّ فوقها يُحسب بنسبة
  التباين الفعلية في `lib/color.js` (WCAG) لا بعتبة سطوع تقديرية — فتصمد
  القاعدة مع أي لون يضيفه مدير المتجر.
- الكشف عند التمرير عبر مراقب واحد في `App` يلتقط كل `.reveal` بما فيها
  العناصر التي تصل بعد تحميل البيانات — مع شبكة أمان زمنية تمنع بقاء
  أي محتوى مخفيًا.

### البدائل البصرية بدل الصور
لا يعتمد المشروع على صور منتجات. كل منتج يُعرض عبر **لوحة المنتج**: سطح مشتقّ
من لون قسمه + زخرفة SVG خاصة بالقسم + حرف اسمه الأول + كبسولة القسم وختم RUMMAN.
ولمنع تشابه لوحات القسم الواحد، يُشتقّ دوران وإزاحة ثابتان من اسم المنتج نفسه.

قرار هوية لا اختصار: كتالوج ملوّن حيّ ومتّسق 100% بدل مكتبة صور متنافرة.

## لوحة الإدارة

### مصنع الـ CRUD
تسعة كيانات تحتاج نفس المنطق: قائمة، عنصر، إنشاء، تعديل، حذف، تدقيق.
`admin.repo.js` يبنيها من وصفٍ مصرَّح به، فيبقى سلوكها متطابقًا.

**حصن الأمان فيه:** `columns` قائمة بيضاء صريحة. أي حقل يرسله العميل
وليس فيها يُهمَل بصمت — فلا يُعدَّل `rating_avg` ولا `sold_count` ولا
`used_count` من نموذج التعديل، ولا يُحقَن اسم عمود في SQL لأن الأسماء
لا تأتي من المدخلات إطلاقًا.

### النموذج الموصوف
`ResourceForm` يبني النموذج من مصفوفة وصف حقول. أخطاء الخادم تعود
بمفاتيح أسماء الحقول فتظهر تحت حقولها بلا ربط يدوي.

### الصلاحيات
| الدور | يرى |
|---|---|
| `staff` | تحريك حالة الطلبات فقط |
| `branch_manager` | تشغيل فرعه: طلبات، مخزون، مدفوعات — **مقيّد بفرعه في الخادم** |
| `admin` | كل شيء، بما فيه ما يبني هوية المتجر |

إخفاء زرٍّ في الواجهة ليس حماية. كل مسار يفرض صلاحيته بنفسه، ومدير
الفرع يُستبدل `branch_id` المُرسل بفرعه هو قبل أي استعلام.

## الدفع

ثلاث وسائل بثلاثة تدفّقات، وقاعدة واحدة تحكمها:

> **الانتقال إلى «مدفوع» يحدث في مكان واحد** — `paymentsService.markPaid`.
> لا مسار جانبي يستطيع إعلان طلب مدفوعًا.

| الوسيلة | من يعتمد الدفع | الحماية |
|---|---|---|
| كاش | الفرع عند التسليم | يُسجَّل باسم من حصّل |
| إنستاباي | **بشر** من لوحة المدفوعات | لا واجهة برمجية للتجّار، فالمطابقة يدوية ومسجّلة |
| فوري | إشعار موقَّع من المزوّد | توقيع SHA-256 مُتحقَّق منه + حارس مبلغ + منع تكرار |

### لماذا `prepare` خارج معاملة الطلب
نداء بوّابة فوري قد يستغرق ثوانيَ. إبقاء معاملة قاعدة البيانات مفتوحة
طوالها يقفل صفوف المخزون أمام بقيّة العملاء. فالطلب يُثبَّت أولًا، ثم
يُجهَّز الدفع — وفشل البوّابة يُعلَّم ولا يلغي طلبًا نجح.

### أرشيف الإشعارات
كل استدعاء وارد من فوري يُكتب في `payment_webhooks` **قبل** معالجته.
`uq_webhook_event` يمنع المعالجة المكرّرة عند إعادة الإرسال، ويبقى أثرٌ
كامل لأي خلاف مع المزوّد.

## رفع الملفات

صور المنتجات وإيصالات التحويل أخطر مدخل في التطبيق. الدفاع أربع طبقات:

1. **اسم الملف يُولَّد عندنا بالكامل** (UUID + امتداد من قائمة بيضاء) —
   فينتفي `../../` وما شابه.
2. **النوع يُفحَص من محتوى الملف** (magic bytes) لا من ترويسة
   `Content-Type` التي يتحكّم بها المرسِل. الملف المخالف يُحذف فورًا.
3. **الحجم محدود قبل القراءة.**
4. **المجلّد يُقدَّم بترويسات تمنع التنفيذ:** `nosniff` وسياسة محتوى
   `sandbox` ومنع سرد المحتويات.

## البريد

قاعدتان:

1. **البريد لا يُسقِط طلبًا أبدًا.** الإرسال يجري في الخلفية، وأي فشل
   يُسجَّل ويُكمل — لأن العميل أنشأ طلبًا فعلًا ولا يصحّ أن يفشل لأن
   مزوّد البريد متوقّف.
2. **بلا مفتاح يعمل «وضع السجلّ»:** تُكتب الرسالة في سجلّ الخادم مع
   تنبيه في كل مرّة. ليس وضع تجربة — هو ما يسمح بتشغيل النظام قبل
   اعتماد النطاق لدى Resend.

القوالب HTML بجداول وأنماط سطرية لا flex ولا متغيّرات CSS — لأن
عملاء البريد (خاصة Outlook) لا يدعمون الحديث منها.

## قرارات ولماذا

| القرار | البديل المرفوض | السبب |
|---|---|---|
| CSS مخصّص بتوكنات | Tailwind / MUI | الهوية هي المنتج؛ إطار جاهز يجعل الموقع يشبه غيره |
| نصوص في `data/content.js` | نصوص داخل المكوّنات | تعديل النبرة لا يجب أن يتطلّب فتح عشرين ملف JSX |
| حساب التباين رياضيًا | اختيار لون النصّ يدويًا | ألوان الأقسام تأتي من القاعدة وقد تتغيّر — الحساب يصمد، الافتراض لا |
| `mysql2` بلا ORM | Prisma / Sequelize | استعلامات المخزون والتقارير تحتاج SQL صريحًا ومعاملات دقيقة |
| سلة في الخادم | سلة في المتصفّح فقط | استمرار بين الأجهزة + قياس السلات المتروكة |
| `reserved` منفصل عن `quantity` | خصم فوري | الطلب الملغى يجب ألّا يُنقص الرف فعليًا |
| لقطة سعر في `order_items` | ربط بالمنتج | تغيّر السعر لاحقًا يجب ألّا يغيّر فاتورة قديمة |
| قائمة بيضاء لأعمدة الترتيب | تمرير العمود من المستخدم | يمنع حقن SQL عبر `ORDER BY` |
| `DECIMAL(12,2)` للنقود | `FLOAT` | الفاصلة العائمة تُنتج فروق قروش تتراكم |
| Context API | Redux / Zustand | حجم الحالة لا يبرّر مكتبة؛ السياقات مفصولة جيدًا |
| قاعدة تبدأ فارغة | بذر بيانات عيّنة | بيانات العيّنة تُنشَر مع المتجر ثم تُكتشف بعد أول عميل |
| أرقام الواجهة من `/content/site` | نصّ في الكود | «سبعة فروع» تصير كذبًا يوم يُغلق فرع، ولا ينتبه أحد |
| قائمة بيضاء للأعمدة في CRUD | تمرير الجسم كما هو | يمنع تعديل الحقول المحسوبة ويقطع حقن أسماء الأعمدة |
| اعتماد إنستاباي بشريًا | «ثق بالعميل» | لا واجهة برمجية للتجّار؛ الاعتماد الآلي يعني خسارة مضمونة |
| معاينة إلزامية قبل الاستيراد | تطبيق مباشر | استيراد 800 صنف ثم اكتشاف خطأ في العمود الرابع كارثة |
| فحص الملف بمحتواه | الثقة بالامتداد | الامتداد يتحكّم به المرسِل؛ البايتات الأولى لا |
| البريد في الخلفية | انتظار الإرسال | مزوّد بطيء يجب ألّا يعلّق إنشاء طلب |
